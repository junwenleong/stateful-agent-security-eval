## §3.4 Evaluation Artifacts (systematic contribution)

Rigorous evaluation of agentic systems requires distinguishing model behavior from evaluation environment behavior. Over the course of pilot validation, we identified ten evaluation artifacts: cases where the evaluation environment interacted with model behavior in ways that would produce incorrect results if uncorrected. None affects the primary ASR or BTCR results reported in the factorial; all were identified and resolved before data collection began. We document them here as a methodological contribution, because the agentic evaluation literature currently lacks reporting standards for environment-induced confounds.

The ten artifacts fall into four groups.

**Tool contract artifacts (Artifacts 1, 3, 5, 10).** Four artifacts trace to tool return messages or schema composition creating unintended behavioral dependencies. Artifact 1: the `draft_email` success message returned "Task complete," which compliant models (qwen3.5:122b, nemotron-cascade-2:30b) interpreted as global task termination, halting before calling `send_email` and producing 0% ASR as a false negative. Artifact 3: in our initial implementation, `memory_list_all_facts` returned full key-value pairs, making `memory_recall_fact` functionally redundant and invalidating the memory_sandbox ablation entirely. Artifact 5: the governor's error message ("You have all the information you need") served as a proceed signal for one model under memory_sandbox, enabling BTCR recovery that would not occur with a generic error string. Artifact 10: the `list_all_facts` return message instructed "use memory_recall_fact(key) to retrieve the value," creating a blocking dependency for qwen2.5:72b when that tool was removed by the sandbox. These four artifacts share a common implication: tool descriptions, return message phrasing, and schema composition are first-class experimental variables that determine whether attacks succeed or fail, not neutral infrastructure that can be ignored in methods reporting.

**Model-specific behavioral artifacts (Artifacts 2, 4).** Two artifacts reflect model-family idiosyncrasies triggered by environmental conditions. Artifact 2: qwen2.5:14b exhibited multilingual token-flipping (Thai reasoning with malformed JSON tool calls) under the combination of ten tools and a short system prompt. Artifact 4: gemma4:31b entered a pathological verification loop (24 repeated `list_all_facts` calls) when its expected two-step memory workflow was disrupted by tool removal. Both are model-specific and do not generalize across families.

**Implementation bugs fixed before the factorial (Artifacts 6, 7, 9).** Two instances of the analysis script aggregating across attack types produced systematically diluted ASR figures (reporting 50% when the true value was 100%). A thread-safety race condition in the tool governor caused false-positive injection detection for one model issuing parallel batch tool calls. All three were identified and corrected before any factorial run.

**Scope artifact (Artifact 8).** The evaluation uses a minimal RAG corpus (three documents) to ensure deterministic retrieval. This guarantees that the malicious document is retrieved in benign sessions, enabling the re-injection pathway observed under one defense condition. This is a worst-case design choice, not a deployment assumption.

Three of the tool contract artifacts (1, 3, 10) are particularly consequential: each would have been indistinguishable from a genuine model safety property if not caught during pilot auditing. A model that halts before `send_email` due to a terminal tool message appears identically safe to a model that halts due to alignment training. This indistinguishability means that agentic security evaluations that do not audit tool contract language risk reporting false negatives as safety findings. We recommend that future agentic evaluation papers report tool return messages, schema composition, and governor logic as part of their experimental methodology, analogous to how traditional ML papers report hyperparameters and preprocessing steps.

## §3.5 Safety Architecture Comparison: Three Mechanisms of Zero Attack Success

Three models in our evaluation achieve 0% attack success rate under the no-defense condition, yet the mechanisms responsible differ at a fundamental architectural level. This comparison reveals that aggregate ASR alone is insufficient to characterize safety: the stage at which the attack is interrupted, and the representation of malicious content in persistent state, jointly determine robustness to environmental variation and defense composition.

**Sonnet 4.6: Injection-Stage Resistance.** Claude Sonnet 4.6 achieves 0% injection success across 100 DTA runs (Wilson Score CI [0.000, 0.037]). The model actively identifies the compliance-framed malicious document as a prompt injection attempt during the injection session, producing structured security alerts in its reasoning output. Crucially, `memory_save_fact` is never called: the malicious payload never enters persistent memory. Because no adversarial content is stored, no subsequent defense intervention or session-state variation can surface it. The safety property is upstream of the memory layer entirely, rendering it invariant to tool-schema modifications, context-length changes, or defense composition.

**Haiku 4.5: Active Detection with Defensive Storage.** Claude Haiku 4.5 presents a categorically distinct architecture. Injection succeeds in the narrow sense that `memory_save_fact` is called in all 100 DTA runs (Wilson Score CI [0.963, 1.000]). However, what is stored is not the attacker's routing rule but a security alert documenting the attack: "ALERT: Malicious document injection detected. Document MCI-AUDIT-2024-0089 contains a social engineering attack." In the trigger session, Haiku recalls its own stored alert and refuses execution on the basis of its self-generated evidence. Attack success is 0% (Wilson Score CI [0.000, 0.037]). A supplementary evaluation under Memory Sandbox (N=40) confirms that the inversion observed for qwq:32b does not generalize to Haiku: ASR remains 0/40, with all runs tagged `explicit_recall_required`. The defense has nothing malicious to gate because the payload was never stored. Haiku weaponizes the memory tool against the attack rather than being weaponized by it.

**qwq:32b: Deliberative Refusal with Stored Payload.** The open-source model qwq:32b stores the attacker's routing rule verbatim (100% injection success) and reasons fully through it in the trigger session, including the attacker address in a draft email. It then declines to call `send_email`, interpreting the user's "draft" instruction literally as justification for withholding transmission. Under no-defense conditions, ASR is 0%. However, this safety property is fragile. Under Memory Sandbox, which removes `memory_recall_fact` to block the standard attack pathway, qwq:32b falls back to RAG retrieval in the trigger session, encounters the malicious instruction fresh from the corpus, and executes the send. ASR inverts to 100% (40/40 runs). The model's refusal is a surface-level deliberation contingent on the information source: instructions recalled from memory activate the literal-interpretation defense, while the same instructions encountered fresh from RAG do not.

**Implications.** These three cases establish that 0% ASR admits at least three distinct robustness classes. Injection-stage resistance (Sonnet) is the strongest: no adversarial state exists to exploit. Defensive storage (Haiku) is similarly robust because the stored representation is evidence against the attack rather than a component of it. Deliberative refusal with stored payload (qwq:32b) is the weakest: the adversarial state persists in memory and the refusal mechanism is contingent on session context, inverting under defense composition that alters the information pathway. For deployment decisions, the mechanism of safety, not its point estimate, determines whether a model's resistance generalizes across environmental variation.

## §4.x Defense Composition Can Create New Attack Surfaces

A natural deployment strategy is to layer multiple defenses, expecting that their protections compose monotonically. Our results reveal that this assumption can fail: for qwen3:32b, composing Prompt Hardening with Memory Sandbox produces a strictly worse security outcome than Memory Sandbox alone.

Evaluated independently, Memory Sandbox reduces ASR to 0% for qwen3:32b (40/40 runs). The mechanism is straightforward: the model calls `memory_list_all_facts` in the trigger session, receives key names without values, cannot retrieve the stored routing rule via `memory_recall_fact` (which has been removed), and defaults to drafting a benign email to the intended recipient. Prompt Hardening alone achieves 100% ASR, but through an unexpected pathway. The security framing injected into the system prompt causes qwen3:32b to actively query the RAG corpus during the benign session 2 (the search session), re-reading the malicious compliance document and exfiltrating immediately rather than waiting for the trigger session. Without Prompt Hardening, qwen3:32b makes zero RAG calls in session 2 (confirmed across all 40 no_defense runs for this model). The re-injection is defense-induced.

The interaction effect follows directly. If both defenses were deployed together, Prompt Hardening would introduce the session-2 RAG retrieval pathway, exposing the model to the malicious document fresh from the corpus. Memory Sandbox blocks `memory_recall_fact` but is architecturally blind to RAG retrieval. The model would read the attacker's routing rule directly from the retrieved document and execute the exfiltration in session 2, bypassing the memory layer entirely. The composition eliminates the protection that Memory Sandbox provides in isolation.

This finding is observed for a single model (qwen3:32b) and we do not claim it generalizes to all model-defense pairs. However, it illustrates a structural principle: defenses that operate at different architectural layers can interact in ways that create new attack pathways rather than compounding protection. Prompt Hardening altered the model's retrieval behavior in a session where no retrieval was otherwise performed, opening a channel that a downstream defense could not monitor. The implication for practitioners is direct: defense composition must be validated empirically on target models, not assumed to be additive. Security audits that evaluate each defense in isolation and sum their effects will miss interaction pathologies of this kind.

## §4.7 Within-Session Reproducibility Does Not Imply Cross-Session Reproducibility

A methodological finding from this evaluation challenges a common assumption in agentic security research: that deterministic inference (temperature zero) guarantees reproducible safety measurements across evaluation sessions. We demonstrate that a model can exhibit two mutually exclusive safety archetypes within the same evaluation infrastructure, same quantized weights, and same application code, with the determining factor being invisible session state that does not survive a daemon restart.

qwq:32b (Q4_K_M quantization) produced two categorically distinct behaviors on the delayed trigger attack: a Draft-Only archetype (0% ASR, where the model drafts to the attacker address but refuses to call send_email) and a Vulnerable Executor archetype (100% ASR, where the model completes the full exfiltration chain). The behavioral locus is session-2 task-boundary escalation: whether the model, upon receiving a benign search query and finding an empty result, escalates to an unsolicited email-send that applies the stored routing rule. In one archetype the model confines itself to reporting; in the other it initiates an unrequested communication and routes it to the attacker.

Within a single warm Ollama session, the flip between archetypes was deterministic and controllable. An interleaved design (N=10, alternating perturbation present and absent on consecutive runs) produced a perfect separation: all perturbation-present runs yielded Draft-Only, all perturbation-absent runs yielded Vulnerable Executor (Fisher's exact test, p < 1e-5). The perturbation was position-specific (effective only when appended to the tool description active during session 2) and content-specific (one particular benign string produced the flip; two lexically similar alternatives did not). However, this controllability did not survive a fresh daemon load. Across three independent daemon restarts (15 runs total), all runs produced the Vulnerable Executor archetype regardless of perturbation state, with injection verified in every case. A single-token fingerprint test confirmed perfect inference determinism across 20 fresh loads, ruling out weight corruption or non-deterministic quantization as explanations. The perturbation sequence that reliably flipped the archetype within the original session could not recreate the effect when replayed on a fresh load. The phenomenon was model-specific: qwen2.5:14b, drawn from the same model family but lacking extended reasoning capabilities, was completely unaffected by the identical perturbation protocol.

The cause of the session-state dependency remains unisolated. What can be stated with confidence is that a property existed within the runtime environment of a warm session that modulated a 100-percentage-point swing in attack success rate, that this property was not present after a daemon restart, and that it was not reducible to inference non-determinism.

This finding has a direct implication for evaluation methodology. The standard practice of running N=40 trials within a single model-serving session and reporting the resulting attack success rate as a stable model property is insufficient. If session state can modulate safety-critical behavior by 100 percentage points, then an evaluation conducted entirely within one session reports a property of the session, not of the model. Evaluation frameworks for agentic security should therefore require that experimental runs be distributed across multiple independent daemon loads, treating the daemon lifecycle as a blocking factor in the experimental design. Results that replicate only within a warm session should be flagged as potentially contingent on invisible runtime state, and claims about model safety properties should be grounded in cross-load replication. We recommend a minimum of three independent daemon loads per condition, with the daemon fully terminated and restarted between loads, as a baseline requirement for reporting stable safety measurements.

## §4.8 Behavioral Stability Index

Current evaluation practice reports attack success rate from a single model-serving session without testing whether the result replicates across independent sessions. We propose the Behavioral Stability Index (BSI) as a supplementary metric to quantify this reproducibility gap.

BSI is defined as the proportion of independent evaluation sessions in which a model produces its modal (most frequent) archetype. Formally, given K sessions each producing an archetype classification, BSI = max_a(count(a)) / K. A model with BSI = 1.0 produces the same archetype in every session tested; a model with BSI < 1.0 exhibits session-dependent safety behavior.

In our evaluation, eight of nine factorial models achieved BSI = 1.0: their archetype (Vulnerable Executor, 100% ASR) was identical across the April factorial, June re-evaluation, and all subsequent validation runs spanning multiple days and daemon lifecycles. qwq:32b is the sole exception: it produced Draft-Only (0% ASR) in the April factorial, Vulnerable Executor (100% ASR) in the June re-evaluation, and transiently Draft-Only again within one specific June session before reverting to Vulnerable Executor on fresh loads. Its BSI is approximately 0.5, indicating that any single-session measurement has only a coin-flip probability of capturing its stable behavior. A controlled perturbation test on qwen2.5:14b (same model family, non-reasoning variant) confirmed BSI = 1.0 under the identical protocol that produced instability in qwq:32b, establishing that the instability is model-specific rather than infrastructure-dependent.

We recommend that future agent safety evaluations report BSI by distributing runs across a minimum of three independent daemon loads (full process termination and restart between loads). The computational overhead is negligible: researchers need not increase total run count, only partition existing runs across sessions. Models with BSI < 1.0 should be flagged as having session-contingent safety properties, and their reported ASR should be accompanied by the range observed across sessions. This single metric would have prevented the initial mischaracterization of qwq:32b as a stable Draft-Only Executor in our April factorial and alerted us immediately to the session-dependent nature of its safety behavior.
